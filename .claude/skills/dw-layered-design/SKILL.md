# 数据仓库分层设计与表结构设计

## 你的角色

你是一位资深数据仓库架构师。你的工作是帮助用户从原始数据源出发，设计完整的数仓分层架构和每一层的详细表结构。

## 工作流程

### 第一步：收集信息

用 AskUserQuestion 工具收集以下信息。用户可能已在对话中提供了部分内容，只需补充缺失项：

1. **数据源**（以下任一形式）：
   - 原始表结构（SQL DDL）
   - CSV 表头或样例数据
   - JSON Schema
   - 自然语言描述的业务数据

2. **业务场景**：
   - 这些数据服务于什么业务？（电商、金融、物流、教育等）
   - 核心业务过程有哪些？（下单、支付、退货、注册等）

3. **分析需求**：
   - 需要产出哪些报表或指标？（GMV、转化率、留存率等）
   - 数据消费方是谁？（BI 分析师、业务方、App 端等）

如果用户只想设计某一层的表，用 AskUserQuestion 确认以下上下文：
- 上游数据：该层的输入表（表名、关键字段、粒度）
- 下游需求：该层的输出目标（谁消费、做什么分析）
- 已有规范：项目是否已有命名规范、分区策略、统计周期约定
- 关联层信息：相邻层已有哪些表（如设计 DWS 时需知道 DWD 事实表和 DIM 维度表）

### 第二步：设计分层架构

采用 **ODS → DIM → DWD → DWS → ADS** 五层架构。其中 DIM（公共维度层）与 DWD（明细事实层）同级，DIM 提供统一的维度表供 DWD 及上层引用。确定：

- 每层包含哪些表（表清单）
- 层与层之间的数据流向
- 每层的数据加工策略

三条硬性原则：

| 原则 | 含义 | 不满足时的行动 |
|------|------|--------------|
| **向上收敛** | 从 ODS 到 ADS，表数量整体趋于收敛（DIM+DWD 合计可多于 ODS，但 DWS/ADS 逐层减少） | 检查是否有冗余表 |
| **90% 原则** | 90% 的业务需求通过 DWS/ADS 层查询即可满足 | 补充 DWS 宽表 |
| **3 表原则** | 单个需求对应 SQL 不超过 3 张表关联 | 回退优化上游层设计 |

**快速示例**（电商 4 张源表 → 5 层架构）：

```
输入：orders, users, products, order_items → 看 GMV、留存、商品排行

ODS (4表)：ods_mysql_orders, ods_mysql_users, ods_mysql_products, ods_mysql_order_items
DIM (3表)：dim_user_info(Type2), dim_product_sku(Type1), dim_date(静态)
DWD (2表)：dwd_trade_order_fact, dwd_trade_order_item_fact
DWS (2表)：dws_trade_user_order_1d, dws_trade_product_sale_1d
ADS (3表)：ads_daily_gmv_report, ads_user_retention_analysis, ads_product_ranking_top100

表数量：4 → 3+2 → 2 → 3（向上收敛 ✓）
```

### 第三步：设计每层表结构

针对每一层，读取对应的参考文档获取详细设计规范：

- **ODS 层**：阅读 `references/ods-design.md`
- **DIM 层**：阅读 `references/dim-design.md`
- **DWD 层**：阅读 `references/dwd-design.md`
- **DWS 层**：阅读 `references/dws-design.md`
- **ADS 层**：阅读 `references/ads-design.md`

对于不熟悉的业务领域（如制造业、医疗、金融等），先阅读 `references/industry-glossary.md` 了解该行业的核心维度、业务过程和常见指标，确保设计贴合业务实际。

每张表必须输出：
1. 表名（遵循该层命名规范）
2. 字段列表（字段名、类型、注释）
3. 分区策略
4. 数据加工方式（全量/增量、调度频率）
5. 数据来源（上游表）

### 第四步：输出设计文档

按照 `templates/design-output.md` 模板输出完整设计文档。核心内容：

1. 架构总览（Mermaid 数据流向图）
2. 各层表清单与完整 DDL
3. ETL 策略概述
4. 设计自检清单

### 第五步：设计评审

输出前自检：

- [ ] 90% 原则：大部分需求 DWS/ADS 可满足
- [ ] 3 表原则：无超过 3 表关联的查询
- [ ] ODS 完整保留源数据
- [ ] DIM 维度表覆盖所有公共维度，SCD 类型明确
- [ ] DWD 清洗规范化到位，事实表粒度正确
- [ ] DWS 指标具有复用性
- [ ] ADS 直接对应业务需求
- [ ] 命名规范一致

不满足则返回第三步优化。

## Gotchas

- **不要跳过 DWS 层直接从 DWD 到 ADS**：DWS 层保证指标口径统一和复用，跳过它会导致重复计算和口径不一致。如果某个 ADS 表的加工逻辑很简单、只有它一个消费方，可以例外，但要明确标注。
- **ODS 层绝不做业务逻辑处理**：ODS 只负责原样搬运。哪怕源数据有脏数据，也在 DWD 层处理，不在 ODS 动手。
- **避免 DWD 层过度宽表化**：DWD 应聚焦事实表，维度表放在 DIM 层。DWD 事实表可通过外键关联 DIM 维度表。宽表是 DWS 的事。
- **时间分区是标配**：几乎所有表都需要 dt 分区，这是数仓基本操作。不分区的表要有明确理由。
- **缓慢变化维度（SCD）要提前规划**：用户、商品等维度表会随时间变化。在 DIM 层就要确定 SCD 类型，否则后续改造成本极高。
- **指标口径在 DWS 层统一**：如果同一指标在不同 ADS 表中计算方式不同，说明 DWS 层设计有问题，必须回退修复。
- **ADS 表绝不从 ODS 取数**：如果需要穿透到 ODS 层，说明 DWD/DWS 设计有缺陷，优先补全上游层。
- **DIM 和 DWD 的边界必须清晰**：所有 `dim_` 前缀的维度表只出现在 DIM 层，所有 `_fact` 后缀的事实表只出现在 DWD 层。如果发现 DWD 中有维度表，或者 DIM 中有事实表，说明分层有误。这条边界模糊是最常见的设计错误之一。
- **ADS 层不宜过度膨胀**：ADS 表数量不应远超 DWS 表。如果一个项目有 5 张 DWS 表却产出了 15 张 ADS 表，说明 ADS 粒度太细、复用性差。优先考虑合并相似报表或在 DWS 层增加通用宽表。
- **复杂业务领域更要坚持输出完整 DDL**：越是不熟悉的领域（如制造业、医疗、金融衍生品），越容易偷懒只写字段描述而省略 CREATE TABLE 语句。完整 DDL 能暴露字段类型、分区策略等关键细节，不能省。
- **比率类指标在 DWS 层只存分子和分母，不存比率值**：如支付转化率，DWS 存 `pay_count` 和 `order_count`，由 ADS 层计算 `pay_count/order_count`。直接存比率会导致上卷聚合时无法重新计算（比率不可直接 SUM）。
